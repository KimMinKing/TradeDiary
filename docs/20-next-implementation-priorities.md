# 다음 구현 우선순위 (2026-10-14)

이 문서는 `feature/ai-trading-journal`의 현재 코드를 기준으로 한다. 구현된 기능을 다시 계획하지 않고, 거래 기록의 신뢰도와 운영 준비를 먼저 높인다. 각 항목은 별도 PR로 나눌 수 있다.

## P0 — 거래 데이터의 범위와 정확도

### 1. 거래소별 수집 범위를 정확히 기록하고 표시

`AdaptiveSyncCoordinator`는 백필 호출이 한 번 성공하면 `history_complete=true`로 바꾸고, Trade Sync 화면은 이를 “History import complete”로 표시한다. 그러나 `TradeService`의 요청 시작일과 각 거래소 API의 실제 조회 가능 기간은 다를 수 있다. 예를 들어 Binance 클라이언트는 요청일이 더 오래되어도 최근 3개월로 시작일을 조정한다. 따라서 현재 플래그는 “요청 가능한 범위의 백필 호출 성공” 이상을 보증하지 않는다.

- 거래소·상품 유형별 `requested_from`, `available_from`, `verified_through`, `last_attempt_at`을 저장한다. 조회 API가 과거 데이터를 제공하지 않으면 그 범위를 명시한다.
- 백필 결과를 `COMPLETE`, `LIMITED_BY_EXCHANGE`, `FAILED`, `PENDING`처럼 구분한다. 기존 `history_complete` 이행 시 과거 행의 범위를 추측해서 채우지 않는다.
- Trade Sync 화면에 실제 보유 기간, 조회 불가능한 과거 기간, 마지막 성공 시각, 다음 재시도 시각을 표시한다. “전체 거래 내역 완료”라는 표현은 확인된 경우에만 사용한다.
- **완료 기준:** 제한된 기간만 반환하는 거래소의 동기화가 성공해도 전체 이력이 확보된 것으로 보이지 않는다. 빈 결과와 API 오류도 구분된다. 날짜 경계·중복 실행 테스트가 있다.

근거: `backend/src/main/java/com/tradediary/sync/AdaptiveSyncCoordinator.java`, `backend/src/main/java/com/tradediary/trade/TradeService.java`, `backend/src/main/java/com/tradediary/exchange/BinanceClient.java`, `frontend/src/pages/TradeSyncPage.jsx`. 거래소 조회 범위는 구현 시 [Binance 선물 API](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade), [Bybit 체결 기록 API](https://bybit-exchange.github.io/docs/v5/order/execution), [Bitget 체결 기록 API](https://www.bitget.com/docs/catalog/trading/order-management)의 최신 문서와 사용 중인 엔드포인트를 대조한다.

### 2. 읽기 전용 거래 대조를 반복 가능한 도구로 만들기

2026-08-12 백업을 이용한 2026-10-11 점검에서는 조회 가능한 Upbit 저장 주문 291건과 Bybit 17건, Bitget 최근 2건이 거래소 응답과 일치했다. 다른 Bybit 키의 11건은 401, 과거 Bitget 건은 조회 기간 제한, Binance는 활성 키 부재로 대조하지 못했다. 이 점검은 백업 이후 누락 거래를 판별하지 못한다.

- 거래소 응답과 DB를 읽기 전용으로 비교해 `일치 / 누락 / 값 불일치 / API 검증 불가 / 조회 기간 밖`을 집계하는 재사용 가능한 검증 명령을 만든다.
- ID, 심볼, 방향, 수량, 가격, 수수료, 시각을 비교한다. 시간대·소수점 정밀도·부분 체결을 명시적으로 처리한다.
- 리포트에는 사용자 식별자, API 키, 원본 응답을 남기지 않는다. 실제 키가 없는 거래소는 검증 불가로 보고한다.
- **완료 기준:** 같은 스냅샷으로 반복 실행하면 같은 결과가 나오고, 누락과 접근 불가를 구분한다. 샘플 응답을 이용한 자동 테스트가 있다.

### 3. 최신 운영 데이터로 복원·마이그레이션 리허설

2026-08-12 로컬 덤프에서는 V102→V117 적용과 거래 본문 보존을 확인했다. 이것은 현재 운영 DB의 상태를 증명하지 않는다.

- 최신 운영 백업을 격리 환경에 복원하고 Flyway `validate` 및 실제 애플리케이션 기동을 확인한다.
- 적용 전후의 사용자·거래·일기 수, 거래 본문 해시, Binance 체결 ID의 고유성을 비교한다.
- 실패 시 복원 절차와 예상 소요 시간을 기록하고, 배포 직전 백업 및 롤백 기준을 정한다.
- **필요한 외부 입력:** 최신 운영 DB 백업 또는 읽기 전용 접근 경로. 제공 전에도 1·2번 구현은 진행할 수 있다.
- **완료 기준:** 최신 운영 스냅샷 기준으로 데이터 불변성과 기동을 검증한 기록이 있다.

## P1 — 결과 검증과 출시 운영

### 4. 포지션·손익 계산의 대조 및 회귀 테스트

현재 `PositionService`는 거래를 심볼과 시간순으로 묶고 반전 거래를 분할하며, 일부 역전·오픈 포지션 테스트가 있다. 누락 체결이나 같은 시각의 체결 순서가 손익과 공개 통계에 미치는 영향은 별도로 검증해야 한다.

- 동일 시각 체결의 결정적 순서, 부분 청산, 반전, 수수료 통화, 선물 포지션 모드를 명시한다.
- 원시 체결 → 포지션 → 통계의 수량·손익 보존을 검증하는 사례를 추가한다. 거래소에서 제공하는 청산 손익과 비교할 수 있는 경우 차이를 보고한다.
- 이력이 `LIMITED_BY_EXCHANGE`이면 전체 기간 수익률을 확정값처럼 보여주지 않는다.
- **완료 기준:** 재계산을 반복해도 결과가 같고, 정해진 사례에서 수량·수수료·손익 합계가 일치한다.

### 5. 동기화 실패를 사용자와 운영자가 해결할 수 있게 만들기

서버에는 `ACTION_REQUIRED`, `BACKOFF`, `failure_count`, `last_error`가 있지만 화면은 일반적인 안내만 보여준다. 에러 문자열을 그대로 노출하면 비밀 정보가 섞일 수 있으므로 분류된 오류 코드가 필요하다.

- 인증 만료·권한 부족·요청 제한·일시 장애·데이터 범위 제한을 구조화된 상태로 변환한다.
- 연결 재설정, 자동 재시도 예정, 수동 재시도 결과를 화면에 구체적으로 표시한다.
- 운영 지표로 마지막 성공 시각, 큐 대기 시간, 실패율, 백필 진행률을 남기고 오래된 데이터에 경보를 건다.
- **완료 기준:** 401과 일시적인 5xx가 서로 다른 해결 행동을 안내하고, 예외 메시지 원문은 사용자에게 노출되지 않는다.

### 6. 전체 서비스 배포와 복구 경로 확정

현재 CI는 백엔드·프론트엔드·AI 서버를 검사하지만 Oracle 수동 배포 워크플로는 백엔드 컨테이너만 교체한다. 프론트엔드와 AI 서버의 실제 운영 배포 방식부터 확인해야 한다.

- 현재 운영 토폴로지와 환경 변수·비밀 값 공급 경로를 문서화한다.
- 실제 운영 방식에 맞춰 프론트엔드와 AI 서버 배포, 서비스 간 헬스 체크, 공개 URL 스모크 테스트를 자동화한다.
- 배포 실패 시 이전 이미지와 DB 백업으로 되돌리는 절차를 리허설한다.
- **완료 기준:** 스테이징에서 세 서비스의 실제 요청 경로를 검증하고 실패 배포를 복구할 수 있다.

## P2 — 제품 기능 확장

### 7. 선택 동의 기반 매매 알림

`docs/17-follow-trade-alert-copy-architecture.md`의 Phase 1을 따른다. 발행자의 매매 공유 동의, 팔로워별 알림 설정, 체결 이벤트의 중복 방지, 인앱 전달부터 구현한다. 발행자 한 명을 팔로워 수만큼 거래소에 조회하지 않도록 수요 기반 동기화 우선순위를 둔다. **완료 기준:** 한 체결이 구독자에게 한 번만 전달되고, 발행자가 공유를 끄면 새 알림이 중단된다.

### 8. AI 조언의 검증 가능성과 피드백

이미 있는 일기 피드백과 트레이더 유형 코칭에 대해 입력 데이터의 기간·표본 수·생성 시각을 표시하고, 사용자 피드백과 품질 평가 사례를 모은다. 수집 범위가 제한되거나 표본이 적을 때는 단정적인 조언을 피한다. **완료 기준:** 같은 평가 사례에서 부정확한 수치·존재하지 않는 거래 인용·민감 정보 노출을 자동 점검할 수 있다.

Auto Copy는 별도 주문 실행 시스템이다. 조회 전용 키와 주문 권한 키의 분리, 위험 한도, 감사 기록, 비상 중지가 설계·검증되기 전에는 이 목록의 착수 대상으로 두지 않는다.

## 권장 착수 순서

1. P0-1의 수집 범위 모델과 화면 문구를 구현한다.
2. P0-2의 읽기 전용 대조 도구를 만들고 P1-4의 계산 사례를 보강한다.
3. 최신 운영 백업이 준비되면 P0-3을 수행한다.
4. P1-5·6으로 운영 흐름을 완성한 뒤 P2 기능을 시작한다.

`docs/00-current-status.md` 등 오래된 현황 문서의 미구현 표시는 현재 코드와 다시 대조해 갱신한다. 이 문서의 우선순위와 완료 기준을 새 작업의 기준으로 사용한다.
